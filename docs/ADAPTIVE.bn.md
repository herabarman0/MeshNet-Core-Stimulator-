# অ্যাডাপ্টিভ মেশ: গতিশীল টপোলজি, লোকেশন সার্ভিস, এনার্জি, কনজেশন, ডিউটি সাইকেল

সব ফিচার **ডিফল্টে বন্ধ**। বন্ধ থাকলে আচরণ আগের সংস্করণের সাথে হুবহু এক (সিমুলেটরে আগের ও নতুন কোডের আউটপুট মিলিয়ে যাচাই করা হয়েছে)।

## ১. কী কী যোগ হয়েছে

| ফিচার | ক্লাস / ফ্ল্যাগ | কী করে |
|---|---|---|
| HELLO বীকন (৫ বাইট) | `Beacon`, `beaconMs` | ব্যাটারি, চার্জিং, লোড, মুভমেন্ট ক্লাস, সিকোয়েন্স নম্বর পাঠায়। বদলালে পাঠায়, না বদলালে `6×beaconMs` পরপর |
| লিংক মেট্রিক | `NeighborInfo` | বীকন লস থেকে B.A.T.M.A.N.-ধাঁচের উইন্ডো, ETX, RSSI-র ঢাল (দ্রুত/ধীর EWMA) থেকে লিংকের আয়ু অনুমান, ACK-ভিত্তিক সফলতার হার |
| মাল্টিপাথ (AOMDV-ধাঁচ) | `MultiRouteTable`, `adaptiveRouting` | ফ্লাডের ডুপ্লিকেট কপি বিকল্প নেক্সট-হপ হিসেবে জমা থাকে; প্রথম পথ ভাঙলে নতুন ফ্লাড ছাড়াই পরেরটা |
| পাথ বাছাই | `PathSelector` | খরচ = (হপ−১) + প্রথম হপের খরচ (ETX × এনার্জি × লোড × মুভমেন্ট × ব্যর্থতা)। কাছাকাছি খরচের মধ্যে ওজনসহ র‍্যান্ডম, যাতে এক নোড ক্ষয় না হয় |
| এনার্জি-অ্যাওয়ার | `energyAware` | দুর্বল ব্যাটারি এড়ানো, দুর্বল নোড ফ্লাডে কম রিলে করে, ব্যাটারি `energyRelayCutoff`-এর নিচে হলে রিলে করতে অস্বীকার (ACK ও জরুরি প্যাকেট ছাড়া) |
| কনজেশন কন্ট্রোল | `congestionControl`, `LoadMeter` | লোড বেশি হলে কম-অগ্রাধিকারের প্যাকেট ফেলে দেয়, লোড বীকনে জানায় যাতে অন্যরা এড়ায় |
| ডাইনামিক টপোলজি | `mobilityAware` | লিংক ভাঙার আগেই ফেডিং লিংক এড়ানো; জোন বদলানো নোডের জন্য ফরওয়ার্ডিং পয়েন্টার; ACK টাইমআউটে গন্তব্যের লোকেশন আবার খোঁজা |
| গসিপ লোকেশন | `GossipDirectory` | ভার্সন-সহ রেকর্ড (LWW), সীমিত ব্যাসার্ধে পুশ + digest/want দিয়ে মেরামত |
| DHT লোকেশন | `DhtNode` | Kademlia, হ্যাশ করা আইডি, ভার্সন-সচেতন লুকআপ ও কোরাম |
| ফ্যাসাড | `MeshServices` | গসিপ (টাইপ ৭) ও DHT (টাইপ ৮) কন্ট্রোল প্যাকেট একসাথে বসায় |
| অ্যাডাপ্টিভ ডিউটি সাইকেল | `kit/AdaptiveDuty` | প্রতিবেশী কম বা ব্যাটারি কম হলে স্ক্যান ইন্টারভাল ধাপে ধাপে বাড়ে |
| গতি পরিমাপ | `kit/SpeedTracker` | লোকেশন থেকে গতি বের করে মুভমেন্ট ক্লাস দেয় |

## ২. ব্যবহার

```java
// কোর: কনফিগে চালু করুন
MeshConfig c = new MeshConfig();
c.adaptiveRouting = true;  c.beaconMs = 10_000;   // মাল্টিপাথ + লিংক মেট্রিক (বীকন ছাড়া লস/ব্যাটারি জানা যায় না)
c.energyAware = true;  c.congestionControl = true;  c.mobilityAware = true;

// কিট: মোবাইলের জন্য তৈরি সেট
builder.tune(Presets.mobileAdaptive());

// অ্যান্ড্রয়েড কিট
MeshNet.Options o = new MeshNet.Options();  o.adaptive = true;

// বিকেন্দ্রীভূত লোকেশন সার্ভিস
MeshServices svc = MeshServices.install(node, clock, rng);
svc.start();  svc.bootstrap(seedNodeId, seedZone);
svc.resolve(nodeId, (id, zone) -> { /* zone == -1 হলে পাওয়া যায়নি */ });
```

নোট: আরএসএসআই পেতে রেডিও থেকে `onLinkQuality(peer, rssi)` ডাকতে হয় (অ্যান্ড্রয়েডে `NearbyRadio` ডাকে)।

## ৩. পরীক্ষার ফল (সৎ হিসাব)

**টেস্ট:** কোর ৫১, লোকেশন সার্ভিস ২৩, সই-করা রেকর্ড ১৪, কিট ১০৭ (+১৭ অ্যাডাপ্টিভ) — সব পাস, কোনো ফেল নেই। আগে থেকে ফেল করা কিট টেস্টের কারণ ছিল সংকুচিত ফ্রেমে চেকসাম না থাকা (নষ্ট ডেটা চুপচাপ ভুল পাঠ হতো); এখন CRC32 যোগ হয়েছে। (ফ্রেম ফরম্যাট বদলেছে: সংকুচিত ফ্রেমের শেষে ৪ বাইট CRC, পুরোনো সংস্করণের সাথে সংকুচিত ফ্রেম মিলবে না।)

**নিয়ন্ত্রিত টেস্টে যা প্রমাণিত:**
- দুর্বল (১৫%) ব্যাটারির রিলে এনার্জি-অ্যাওয়ার মোডে প্রায় ০% ট্রাফিক পায়; ছাড়া ২৫%+।
- নীরবে একটি পথ ভাঙলে ৬০টির ৬০টি মেসেজই পৌঁছায়; রি-ট্রাই ক্লাসিকের কাছাকাছি (৪ বনাম ৩)। ACK ফেরার পথের ক্ষতি ধরার জন্য রিসিভার পুনরাবৃত্ত মেসেজ দেখলে সেই পথকে দোষ দেয়।
- ফেডিং লিংক ভাঙার আগেই এড়ানো: মুভমেন্ট-অ্যাওয়ার ছাড়া ২২% ট্রাফিক, চালু থাকলে ০%।
- জোন বদলানো নোডের কাছেও ফরওয়ার্ডিং পয়েন্টারে ডেলিভারি।

**সিমুলেটর (৫০০ নোড, ২০% খারাপ লিংক):**
- ক্লাসিক ৯৯.৬% → অ্যাডাপ্টিভ ৯৭.৭%। **অর্থাৎ ডেলিভারিতে লাভ নেই; বীকনের খরচ (হ্যালো ~৮০% বেশি) বরং কিছুটা ক্ষতি করে।**
- ব্যাটারি পরীক্ষা (বেশি ড্রেন): ব্যাটারি শেষ হয়ে মৃত নোড ক্লাসিক ৩৫, অ্যাডাপ্টিভ (এনার্জি ছাড়া) ৬৯, এনার্জি-অ্যাওয়ার ৭। দাম: ডেলিভারি ৯৯% → ৯১.৫%। নেটওয়ার্কের আয়ু বাড়ে, কিন্তু কিছু মেসেজ হারায়।
- `energyRelayCutoff` বাড়ালে আয়ু আরও বাড়ে, ডেলিভারি আরও কমে — প্রয়োজন অনুযায়ী ঠিক করুন।

## ৪. সীমাবদ্ধতা

- লাভ ছোট ফ্ল্যাট নেটওয়ার্কে কম; গসিপ/DHT বড় জোনভিত্তিক নেটওয়ার্কে কাজে লাগে।
- অ্যান্ড্রয়েড কোড (`NearbyRadio`, `LocationFeeder`, `MeshNet`) এখানে কম্পাইল ও ডিভাইসে পরীক্ষা করা যায়নি — আপনার ফোনে বিল্ড করে দেখতে হবে।
- RSSI-ভিত্তিক আয়ু অনুমান সিমুলেটর/টেস্টে যাচাই; বাস্তব রেডিওর RSSI গোলমাল বেশি, সীমা (`linkExpiryHorizonMs`, ঢাল −০.৮ dBm/s) ফিল্ডে টিউন করতে হবে।
- অ্যাডাপ্টিভ বীকন পুরোনো নোডের সাথে মিশে চলে (বীকনহীন নোড "নিরপেক্ষ" ধরা হয়)।

## ৫. সই-করা লোকেশন রেকর্ড (অথেনটিকেশন)

```java
MeshServices svc = MeshServices.install(node, clock, rng, new IdentityRecordAuth(identityKeys));
```

- প্রতিটি গসিপ/DHT লোকেশন রেকর্ড মালিকের ECDSA কী দিয়ে সই হয়; সই ও পাবলিক কী রেকর্ডের সাথে যায়, রিলে নোডরা অপরিবর্তিত পাঠায়।
- যাচাই ব্যর্থ হলে (ভুয়া সই, মান বদলানো, অন্য কী) রেকর্ড ফেলে দেওয়া হয়। DHT-তে স্টোর ও লুকআপ দুই জায়গাতেই যাচাই হয়, তাই মিথ্যাবাদী রেপ্লিকা গণনায় আসে না।
- একই আইডির জন্য প্রথম দেখা কী বাঁধা থাকে (TOFU); পরে অন্য কী দিয়ে দাবি করলে প্রত্যাখ্যাত।
- **প্রথম-যোগাযোগের ফাঁক বন্ধ করার দুটি উপায়:** `guard.pin(id, key)` (বিশ্বস্ত চ্যানেল থেকে পাওয়া কী), অথবা নোড আইডি = `RecordGuard.idOf(publicKey)` ধরে `setIdBoundToKey(true)` — তখন কেউ অন্যের আইডির জন্য সই করতেই পারে না। এর কোনোটি না করলে অদেখা আইডির প্রথম দাবিদার জেতে।
- সই চালু থাকলে প্রতি রেকর্ড ~১৪০ বাইট বড়; একটি বার্তায় কম রেকর্ড যায় (সফট সীমা ~১০০০ বাইট)। বীকন, মেয়াদ ও ব্যাসার্ধ সই-এর বাইরে (রিলে বদলায়)।
- সই-হীন নোড সই-করা বার্তা উপেক্ষা করে এবং উল্টোটাও — মিশ্র নেটওয়ার্কে দুই দল আলাদা থাকবে।
- যা ঠেকায় না: কোনো নোড রিলে করতে অস্বীকার করা, বা মালিকের নিজের পুরোনো সঠিক রেকর্ড মেয়াদ শেষ পর্যন্ত রিপ্লে করা।
